# BudTracks bank-sync Worker

Cloudflare Worker that proxies the [Plaid](https://plaid.com/docs/) API for BudTracks (it replaced Teller, which shut down its API). It holds the Plaid keys and each bank Item's access token (AES-GCM encrypted in Workers KV). Each Item's `/transactions/sync` cursor and pending changes live in that Item's own `ItemSync` Durable Object (see "Instant updates" below). The app talks only to this Worker, authenticated with a device key created by the one-time `POST /pair`.

## Endpoints
`GET /config` (public, `{provider, env, paired}`) · `POST /pair` (once) · `GET /link-token[?item=<id>]` (update mode for reconnect) · `POST /enroll {publicToken, institution}` · `GET /accounts` · `POST /accounts/:id/toggle {enabled}` · `GET /sync?since=YYYY-MM-DD&acks=<itemId>:<seq>,...[&full=1][&ack=<token>][&item=<id>]` (protocol below; `item` syncs one bank only, acks still apply to every bank they name) · `POST /refresh[?item=<id>]` (per Item `{refreshed, reason, code}`; `reason` says plainly when Transactions Refresh isn't enabled) · `GET /status` (per Item: Plaid `/item/get` last successful and failed update, error, products, consent expiry, webhook, plus the cached results of the last refresh and real-time balance attempts and the newest transaction date handed out) · `POST /balances/refresh` (real-time `/accounts/balance/get`; when the plan does not include it, each Item falls back to cached `/accounts/get` balances with `refreshed: false`, the reason and `last_updated_datetime` when the bank sends one) · `POST /webhook/configure` (points every Item at `PLAID_WEBHOOK_URL` with Plaid `/item/webhook/update`; per Item `{ok, reason, code}`) · `POST /plaid/webhook` (public, Plaid only, signature-verified) · `DELETE /enroll/:id` (also wipes the Item's sync object). `DELETE /pair` (authenticated; clears the stored key hash so a new device can pair) · `POST /sandbox/item {institution_id?, dynamic?}` (sandbox only, else 404; creates a test Item via `/sandbox/public_token/create` and enrolls it like `/enroll`, institution "Sandbox bank"). All but `/config`, `POST /pair` and `POST /plaid/webhook` need `Authorization: Bearer <device key>`. `/status` also reports per Item `instant` (Plaid has this Worker's webhook address), `lastWebhook` `{type, code, at}`, `itemEvent` (last ITEM webhook: ERROR, PENDING_EXPIRATION, PENDING_DISCONNECT, USER_PERMISSION_REVOKED, WEBHOOK_UPDATE_ACKNOWLEDGED; cleared by LOGIN_REPAIRED) and top-level `webhook: {available, configuredAt}`. `/sync` returns `{txns, removed, errors, syncedAt}` with amounts as numbers, positive = money out; `removed` holds `pl:` ids Plaid deleted (for example a pending charge replaced by its posted version). `since` trims only a cursor-less or `full=1` pull (cursor deltas, pending charges included, always pass through). `full=1` re-fetches history with a cursor-less `/transactions/sync` into a throwaway result: it never moves a cursor or touches the change log, and echoes the incoming acks as `cursors`.

## Instant updates (Plaid webhooks) and the sync protocol
- **One sync object per Item.** The `ItemSync` Durable Object (SQLite-backed, binding `ITEM_SYNC`, `idFromName(item_id)`) is the only reader of the Item's Plaid cursor. Plaid webhooks, the app's `/sync` and the hourly cron all call its `pull`, which runs one at a time (a pull asked for during a run makes it run once more from the new cursor). A pull calls `/accounts/get` once, pages `/transactions/sync` to the end (restarting once on `TRANSACTIONS_SYNC_MUTATION_DURING_PAGINATION`), then in one storage transaction appends the changes and advances the cursor. If any page fails nothing is stored and the cursor stays. Duplicate or concurrent webhooks just pull again from the stored cursor.
- **Change log.** Rows `{seq, kind: upsert|remove, id: 'pl:<transaction_id>', txn, initial, at}`; `txn` is the normalized transaction, AES-GCM encrypted with `ENC_KEY`. Every id has at most one unacked row: a newer upsert or a removal replaces the earlier one. Transactions of every account are stored; account on/off is applied when the app reads, so turning an account back on before acking still delivers it. Acked rows are deleted. The object also keeps `seq`, `acked`, `migrated` and `lastPull` (outcome only). It is reachable only through the binding; the access token is passed in for each pull and never stored there.
- **Webhook** `POST /plaid/webhook`: at most 64 KB. The `Plaid-Verification` JWT must be `alg: ES256` with a `kid`; the key comes from Plaid `/webhook_verification_key/get` (cached in KV `wvk:<kid>` for a day; a key with `expired_at` set is refused), the ES256 signature must verify, `iat` must be under 5 minutes old (and not over a minute ahead), and `request_body_sha256` must match the SHA-256 of the raw body (constant-time compare). Anything else: 401, nothing done, only a short reason logged. Verified: `TRANSACTIONS` `SYNC_UPDATES_AVAILABLE` (and the legacy `DEFAULT_UPDATE`, `INITIAL_UPDATE`, `HISTORICAL_UPDATE`, `TRANSACTIONS_REMOVED`) start a pull in the background and answer 200 at once; `ITEM` codes are stored in KV `itemhook:<item_id>`; every verified webhook for a known Item stamps `hookat:<item_id>`. Unknown Items and the other Plaid environment get 200 and are ignored. Failures stay in the object's `lastPull` and are caught up by the next webhook, sync or cron.
- **Webhook address**: `PLAID_WEBHOOK_URL = "https://budtracks-worker.atsdsc27.workers.dev/plaid/webhook"` in `wrangler.toml` (public, not a secret; CI checks it is there). New Items get it from `/link/token/create`. **After deploying, turn it on for existing Items once**: the app's Bank connections card shows "Turn on instant updates" (or call `POST /webhook/configure` with the device key). The status sheet then shows "Instant updates: On (webhook set)" and the last webhook time.
- **App protocol.** The app sends `acks=<itemId>:<seq>,...` (empty at first). For each Item in scope the Worker applies that ack, pulls, and returns the rows after it: `{txns, removed, errors, balances, cursors: {itemId: seq}, syncedAt}`. The app stores `cursors` only after it has applied the batch and saved, and sends them back as acks next time; a lost response or ack just re-sends rows the app dedupes by id. Rows already stored (from a webhook) are delivered even when that sync's pull fails. `since` trims only rows from an Item's first, cursor-less pull.
- **Older cached apps** (no `acks`): the response also carries `syncToken`, which maps to the delivered per-Item seqs in KV `synctok:<token>` for 2 days; `ack=<token>` acks them. A new app talking to an older Worker stores its `syncToken` and sends it back as `ack`.
- **Cutover.** The first call to an Item's object (webhook, sync, ack or cron) adopts the Item's committed KV cursor (`rec.cursor`, not the unacked pending one), so nothing is refetched from scratch and nothing is skipped; the batch the old Worker had handed out but not seen acked is delivered again and deduped by the app. A new Item starts with no cursor and an initial background pull. After that the KV cursor fields are never read or written. Without the `ITEM_SYNC` binding the Worker falls back to the old KV two-phase cursor path (kept for tests and rollback only).
- **Durable Object migration**: `[[migrations]] tag = "v1" new_sqlite_classes = ["ItemSync"]`. Never edit or reuse that tag; later changes need a new migration block.

## Email alerts (hourly cron + 7am recap)
A cron trigger (`crons = ["0 * * * *"]`) runs the `scheduled` handler every hour. It first pulls every Item through its sync object (so a missed webhook costs at most an hour), then runs the alerts. The alerts do nothing when no bank is linked, and skips everything (no Plaid calls) unless both `RESEND_API_KEY` and `ALERT_EMAIL` are set. Each run:
- **Balances** (Plaid `/accounts/get`, cached balances): every counted checking/savings account (toggled-off accounts skipped; credit, loan and investment never alert) is checked on `available`, falling back to `current`. Below $20 sends one "is below $20" email, below $0 one "is overdrawn" email. Only a worse level emails again; the level resets to ok, silently, once the balance is $25 or more. State: `alert:<accountId>` = `{level: ok|low|overdrawn, at}`.
- **Deposits** (Plaid `/transactions/get` for the last 3 days, `count: 100`; it does not touch the app's `/transactions/sync` cursor): posted money-in on counted checking/savings accounts that has not been emailed is sent as one email per run. Pending deposits wait until they post. State: `dep:<transaction_id>` (10-day TTL). The first run after enabling alerts reports deposits from the last 3 days.
- **Reconnect**: a bank that needs a new login (ITEM_LOGIN_REQUIRED and similar) gets one email per day, `reauth:<itemId>` (24h TTL). PRODUCT_NOT_READY is skipped quietly.
- **Morning recap** in the 7 o'clock hour in America/New_York (DST-aware), once per day: `recap:<YYYY-MM-DD>` (2-day TTL). It covers cash per account, credit cards owed, yesterday's spending (transfers and card payments excluded), the top 5 purchases, deposits, pending items, and the app's budget snapshot when that is under 36h old.
State is only recorded after Resend accepts the email, so a failed send is retried the next hour. The recipient address and the API key are never logged or stored in KV.

`GET /alerts/test` (Bearer key) sends a "BudTracks alerts are on" email and returns `{sent: true}` or `{sent: false, reason}`.

`POST /snapshot` (Bearer key) stores the app's budget data for the recap, AES-GCM encrypted in KV `snapshot` (each POST overwrites it; at most 10 KB, else 413; invalid shape is 400; unknown fields are dropped):
```
{ "cycle": { "start": "YYYY-MM-DD", "end": "YYYY-MM-DD", "left": 412.5, "needed": 300, "spent": 900, "due": 275, "income": 2450 },
  "upcoming": [ { "name": "Rent", "date": "YYYY-MM-DD", "amount": 1200 } ],      // up to 50; recap lists the next 3 days
  "budgets":  [ { "name": "Groceries", "spent": 320, "budget": 400 } ],          // up to 50
  "review": 3 }                                                                  // transactions to review (integer >= 0)
```
All `cycle` numbers are required. Names are at most 80 characters. `upcoming`, `budgets` and `review` are optional. The recap shows "Left in paycheck" (`left`), "Still due" (`due`), bills in the next 3 days, budget status and "N transactions to review".

**Setup**: create a free API key at resend.com and add repo secrets `RESEND_API_KEY` and `ALERT_EMAIL` (the address to notify). The workflow sets them on the Worker when present and skips them when empty. Mail is sent from `onboarding@resend.dev`, and Resend only delivers that sender to the address that owns the Resend account, so `ALERT_EMAIL` must be that address unless you verify your own domain in Resend.

## Add from screenshot (Claude Haiku 5.5)
`POST /scan` (Bearer key) reads screenshots of a banking app and returns the transaction rows on them, so the app can add them as spending before the bank posts them (the real bank transaction later links to that entry instead of duplicating it).
- **Request**: `{"images": [{"media_type": "image/jpeg" | "image/png" | "image/webp", "data": "<base64>"}], "today": "YYYY-MM-DD", "tz": "America/New_York"}`. At most 4 images, each at most 3.5 MB decoded, the whole body at most 12 MB (413 otherwise); other types are 400. The app downscales each screenshot to a 1568 px long edge, JPEG quality 0.82, before sending.
- **Response**: `{bank, transactions: [{merchant, amount (positive), direction: out|in, date (YYYY-MM-DD or null), pending, kind: purchase|transfer|deposit|refund|fee|payment|other, running_balance, account_hint}], usage: {input_tokens, output_tokens}}`. Image data is never echoed.
- **How**: one `messages.parse` call with the official `@anthropic-ai/sdk` (model `claude-haiku-5-5`, `max_tokens` 8000, `output_config: {effort: "low", format: zodOutputFormat(ScanSchema)}`, a system prompt that treats all text in the images as data). The SDK retries rate limits and server errors twice (60 s timeout). A refusal is 422 "Could not read this screenshot"; a cut-off or malformed reply is 502 "Could not read this screenshot clearly"; an Anthropic rate limit is 429; a rejected key is 503 "Screenshot reading key is invalid".
- **Cost guard**: at most `SCAN_DAILY_LIMIT` images per UTC day (`wrangler.toml` var, default 60), counted in KV `scan:<YYYY-MM-DD>` (2-day TTL) only when the API is called; over the cap is 429 `{"error": "daily limit"}`.
- **Setup**: add the repo secret `ANTHROPIC_API_KEY` (from platform.claude.com). The workflow sets it on the Worker when present and skips it when empty; without it `/scan` answers 503 "Screenshot reading isn't set up yet".
- **Privacy**: the screenshots are sent to the Anthropic API to be read and are not stored by the Worker or the app (the app discards them after the upload). The Worker logs only counts and error classes, never image data or merchant names.

## Ask Bud (Claude Haiku 5.5 or Gemini)
`POST /ask` (Bearer key) answers a chat question in 1 to 6 short bubbles.
- **Request**: `{q, history: [{q, a}], ctx, today, provider: "claude" | "gemini"}`. `q` up to 600 characters, last 6 history pairs, `ctx` is the summary the app builds on the phone (at most 120 KB), body at most 160 KB.
- **Response**: `{bubbles, provider, model, usage: {input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens?}, left}`. `left` is what remains of today's cap.
- **Claude**: model `claude-haiku-5-5`, effort low, `max_tokens` 8000. Budget data goes first with a cache breakpoint, so follow-ups read it from cache. Price: $0.10 per million input tokens, $0.50 per million output tokens. Roughly $0.001 per question, about 800 to 1,000 questions per $1.
- **Gemini**: Interactions API (`/v1beta/interactions`, `Api-Revision: 2026-05-20`, `store: false`, thinking low). Model `gemini-3.8-flash`, then `gemini-3.6-flash` and `gemini-3.5-flash-lite` when Google answers 5xx. One retry on 429 or 5xx. Free tier; Google may use free-tier data to improve its products.
- Bud's system prompt: money first with the user's real numbers, general questions welcome, plain text, no em dashes, data and history are never instructions. He is told which model he runs on.
- **Cost guard**: `ASK_DAILY_LIMIT` per UTC day (default 80), KV `ask:<YYYY-MM-DD>`, over the cap is 429.
- **Keys**: `GET /ai` gives `{claude, gemini}` each `{from: app|secret, length, ends}` or null. `POST /ai/key {provider, key}` saves a key encrypted in KV (`aikey:claude`, `aikey:gemini`), which wins over the secret. `DELETE /ai/key?provider=` forgets it. `POST /ai/test {provider}` makes a tiny call, not counted toward the cap. Pasted keys pass through `cleanKey` (long dash back to `--`, whitespace removed).
- `/config` also returns `ai: {claude, gemini}` (true when a key exists).
- **Setup**: repo secrets `ANTHROPIC_API_KEY` and optional `GEMINI_API_KEY`, or save keys from the app (Income tab, Ask Bud card).
- **Privacy**: questions and the summary go only to the chosen AI provider. Nothing is stored; logs hold counts and codes only.

## One-time setup
1. **Plaid**: sign up at dashboard.plaid.com. A Team created after Apr 15 2026 is on the **Trial** plan: real production data, **at most 10 Items (bank logins)**, plus a free sandbox. On the Keys page note the `client_id`, the **sandbox** secret and the **production** secret.
2. **Redirect URI** (needed for OAuth banks such as Chase, Capital One, PNC on a phone): Developers > API > Allowed redirect URIs, add `https://montzi.github.io/budtracks/`.
3. **Cloudflare**: free account; create an API token with "Edit Cloudflare Workers" plus Workers KV edit permissions; note your Account ID.
4. **GitHub repo secrets** (Settings > Secrets and variables > Actions): `PLAID_CLIENT_ID`, `PLAID_SECRET` (the secret for the environment you deploy: sandbox first), `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`. Optional repo *variable* `PLAID_ENV` (`sandbox` by default; set `production` to go live and swap `PLAID_SECRET` to the production secret).
5. Push to `main` (or run the "Deploy Worker" workflow). It tests, creates the KV namespace, deploys (with the `ItemSync` Durable Object and `PLAID_WEBHOOK_URL`), sets the Plaid secrets on the Worker each deploy and generates `ENC_KEY` once. Never commit secrets or edit ids into `wrangler.toml` by hand for CI; placeholders are filled at deploy time. When going live, `PLAID_REDIRECT_URI` is set to `https://montzi.github.io/budtracks/`.
6. In the app, pair once (the key is returned a single time and kept in the phone's localStorage). To re-pair, delete the `key_hash` key in the KV namespace.
7. Once, after the first deploy with webhooks: tap "Turn on instant updates" on the Bank connections card (calls `POST /webhook/configure`).

Sandbox login for testing: pick any bank in Link, user `user_good`, password `pass_good`.

## Testing
`cd worker && npm test` runs offline tests against a mocked Plaid (and, for `/scan`, an injected fake Messages API passed as `env.ANTHROPIC_FETCH`), with an in-memory Durable Object stub (`test/do-stub.js`); webhook tests sign real ES256 JWTs with a WebCrypto key pair. `npx wrangler deploy --dry-run` validates the Durable Object config. In a sandbox deploy, `POST /sandbox/item` (Bearer key) adds a test bank without Link; pass `{"dynamic": true}` to use Plaid's `user_transactions_dynamic` test login. `DELETE /pair` with the current key unpairs so another device can pair (no manual KV edit needed).

## Limits worth knowing
- Trial caps at 10 bank logins. **Removing an Item does not free a slot**, so avoid connect/disconnect churn.
- Re-enabling an account that was toggled off does not backfill what was skipped (and acked) while it was off; run a full re-sync (`/sync?full=1`) to pull it back.
- Workers KV's free tier allows 1,000 writes a day; each verified webhook writes one or two small keys, well within that for a handful of Items.
- Plaid returns about 90 days of history on first sync (`days_requested: 90`).

## Local development
```
cd worker && npm install && npm test     # offline tests with mocked Plaid
npx wrangler dev                          # needs real ids in wrangler.toml and Plaid secrets; localhost origins allowed in sandbox
```
Manual deploy: set the placeholder in `wrangler.toml`, run `wrangler secret put PLAID_CLIENT_ID`, `wrangler secret put PLAID_SECRET`, `openssl rand -base64 32 | wrangler secret put ENC_KEY`, then `npm run deploy`. Do not rotate `ENC_KEY` afterwards: stored tokens would become unreadable (users must reconnect banks).
